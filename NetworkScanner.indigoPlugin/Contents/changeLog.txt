Version 2026.5.73 (2026-07-08)

1. Removed the decade-old error filter that suppressed any exception
     whose message contains "None" (all 21 guard sites).  It was hiding
     genuine NoneType bugs - including whatever has been silently
     aborting the ARP sweep mid-cycle on every pass.  Only true Indigo
     reload noise ("UnexpectedNullError -- CClientMgr not created") is
     still suppressed.  All real errors now log at ERROR level with a
     traceback.

================================================================================
Version 2026.5.72 (2026-07-08)

1. Diagnosis aid for the missing ARP-alive metronome: the ARP sweep has
     been dying mid-cycle with a silently swallowed exception (the
     benign-IPC filter matches any message containing "None", which also
     hides genuine NoneType bugs), aborting every sweep BEFORE the cache
     flush and the sweep-complete summary.  Suppressed sweep errors are
     now logged at level 10 with full traceback while the plugin is
     running (shutdown noise stays suppressed).

================================================================================
Version 2026.5.71 (2026-07-08)

1. OFFLINE 9 s after a sighting, again (reported 00:08:02 vs sighting
     00:07:53): the v2026.5.67 cancel-guard compared the live entry
     against snapshot[mac] - but dict(self._known) is a SHALLOW copy,
     so snapshot[mac] IS the live entry object and the comparison could
     never trigger.  The guard now compares against the last_seen value
     the offline verdict was actually based on (carried in the results
     tuple), so any sighting that arrives during the probe pass reliably
     cancels the verdict.
     Root cause of the observed event: the ARP reply at 00:07:53 was the
     phone answering the confirm gate's OWN ARP-liveness ping; the
     concurrent sweep flushed the ARP cache in the same instant, so the
     liveness check read an empty cache and reported dead.  The tcpdump
     capture of that same reply now cancels the false verdict.

Version 2026.5.70 (2026-07-08)

1. scanInterval is now a TRUE sweep period (sweep start to sweep start):
     both scan loops previously slept the full scanInterval AFTER the
     sweep + probe work finished, so with 30-60 s of work per cycle a
     "60 s" setting produced sweeps only every ~2 minutes - widening the
     worst-case detection gap accordingly.  The idle sleep now subtracts
     the work time already spent, with a 15 s minimum idle window so
     back-to-back sweeps can never hammer the network.  Applies to the
     primary and the secondary-interface loop.

Version 2026.5.69 (2026-07-07)

1. Confirm mode reverted to pure last-gate semantics (design decision):
     the ARP/sniff timeout alone declares the device off; the confirm
     ping runs only AFTER that verdict and can only rescue (veto) it -
     it never probes early and never causes an off by itself.  The 10 s
     pre-probe window from v2026.5.63 is removed; the ARP-liveness
     fallback and the watchdog deference remain.

Version 2026.5.68 (2026-07-07)

1. Sleeping-device ARP detection silently inactive (reported: with
     scanInterval=60 the sweep only registered the iPhone when it was
     awake - no "ARP reply (sweep)" sightings at all):
     the v2026.5.57 ARP-alive path only activates after a SUCCESSFUL
     arp -d -a cache flush, judged strictly by exit code 0.  macOS
     arp -d -a frequently exits non-zero even though it deleted most
     entries (some entries refuse deletion), and the failure was
     swallowed silently - so the feature never switched on.
     The flush now counts as successful when the output shows deleted
     entries regardless of exit code, and a genuine failure is logged
     once per session as a WARNING naming the fix (sudo password).

Version 2026.5.67 (2026-07-07)

1. Probe pass stale-snapshot race (reported: OFFLINE at 22:55:26 with
     the log line itself showing "last seen: 22:55:21 = 209s ago" - a
     self-contradiction): _check_all_devices computed its offline
     verdicts from a snapshot taken at the start of the pass and then
     committed them, OVERWRITING last_seen backwards and ignoring
     sightings that the sniff/sweep threads registered while the pass
     (probe + ARP fallback, up to ~30 s) was running.  Same class of
     bug as the watchdog race fixed in v2026.5.59.  The commit now
     re-checks the live entry under the lock: a sighting newer than
     the snapshot cancels the offline verdict, and last_seen can never
     move backwards.

Version 2026.5.63 (2026-07-07)

Confirm-offline mode actually confirms now (reported: device with
"Confirm offline" went OFFLINE [timeout] with no ping activity at all):

1. The offline watchdog fired at the bare last-seen threshold for EVERY
     device, regardless of pingMode - so the confirm-ping never got a
     chance to run.  The watchdog now skips modes where the probe path
     owns the offline decision (confirm / both / offline / pingOnly);
     _check_all_devices (every 15 s) makes the call for those.

2. The confirm probe now starts _CONFIRM_PRE_SECS (10 s) BEFORE the
     threshold expires, so the decision at expiry is based on a real
     probe result.  An early miss cannot take the device down before
     the threshold has actually expired.

3. New ARP liveness fallback: when the confirm ICMP/TCP probe fails,
     the device's ARP is checked directly (cache entry deleted first
     when the sudo password is set, then a ping forces a fresh ARP
     resolution, then the cache must show the device's OWN MAC).
     Sleeping iPhones answer ARP in the Wi-Fi chip while ignoring
     ICMP and TCP, so this keeps a phone that is home ONLINE even
     when it fails the classic ping.  Proxy-ARP cannot fake it (a
     router answers with its own MAC).

4. Gates that could silently defer a due confirm probe (per-device
     onlineCheckInterval, sweep-freshness skip) now let timed-out /
     due-for-confirm devices through.

Version 2026.5.59 (2026-07-07)

1. Offline watchdog stale-snapshot race (reported: device marked OFF at
     21:12:01 although a sighting was logged at 21:11:53):
     the watchdog takes a snapshot of _known at the start of each 15 s
     pass and committed timeout-offline decisions from that snapshot.
     Sightings registered by the sniff/sweep threads DURING the pass
     (which can stretch to many seconds due to per-device Indigo IPC)
     were ignored, so a device could go offline right after it was seen.
     The watchdog now re-reads the live entry under the lock immediately
     before committing and aborts the OFF if last_seen was refreshed in
     the meantime.

1. vendor=Unknown was cached forever: the OUI lookup ran exactly once

Version 2026.5.57 (2026-07-07)

1. Sleeping iPhones no longer drop off after a while (presence parity
     with UniFi / BLE based detection):
     iPhones in Wi-Fi power-save answer ARP requests in the Wi-Fi chip
     (ARP offload) but ignore ICMP ping and TCP probes, so after a few
     minutes of screen-off the sweep saw them only as "in ARP cache but
     no ping reply" - which was treated as stale and never refreshed
     last_seen, so the offline timeout eventually fired even though the
     phone was home.
     When the ARP cache flush (sudo arp -d -a, needs the sudo password
     in the plugin config) ran after the previous sweep, every arp -a
     entry in THIS sweep is a fresh ARP reply - the ping fan-out forces
     an ARP resolution per IP.  Such entries now count as proof of life
     ("replied to ARP only" in the sweep log) and refresh last_seen.
     Proxy-ARP routers cannot fake this: they answer with their OWN MAC,
     so an entry carrying the client's MAC came from the client itself.
     "permanent" entries (the arp -s re-seeds for pingOnly devices) are
     excluded.  Without a recent flush (no sudo password configured)
     cache entries can be ~20 min stale, so the old conservative
     treatment is kept - configure the sudo password to enable this.

Version 2026.5.56 (2026-07-07)

1. Home/Away off-delay never fired (reported: group device never cycles
     OFF with any delay setting, works only with "Immediate"):
     _recalc_group_device is event-driven - it runs when a participant's
     onOffState CHANGES.  When the last participant went offline the
     countdown was started and the group kept its ON state, but with all
     participants already offline no further event ever arrived, so the
     expired countdown was never re-checked and the group stayed ON
     forever.  runConcurrentThread now re-evaluates any group with a
     pending off-delay once per second until it resolves (fires OFF or
     is cancelled by a participant coming home).

Version 2026.5.55 (2026-07-07)

1. ARP sweep / device probe - "TimeoutError: N (of M) futures unfinished":
     the 8 s probe-pool deadline was far too short for a subnet with many
     unused IPs (a dead host costs ~3 s: 1 s ICMP timeout + 4 TCP ports
     x 0.5 s; 254 hosts / 30 workers needs 25 s+), and the uncaught
     TimeoutError aborted the ENTIRE sweep - no arp -a parse, no state
     updates that cycle.  Both probe pools (ARP sweep and known-device
     probe) now catch the timeout, keep the partial results, cancel the
     unfinished probes, and adaptively raise the deadline for the next
     cycle (pluginPrefs "probeDeadline", +15 s per timeout, capped at
     120 s - same pattern as the adaptive arpTimeout).

2. MAC2Vendor.py - removed 11 legacy Python-2 u"..." string prefixes.

Version 2026.5.54 (2026-07-07)

Bug-fix release — full code audit (18 fixes):

1. Passive sniffing (tcpdump) — ARP-Announcement, mDNS, and generic-frame
     parsing blocks were indented one level too shallow, so they ran only
     once per read chunk on the last buffered line instead of once per
     line.  Most mDNS/announcement traffic was silently ignored; passive
     discovery of devices that never send ARP replies was broken.
     Blocks moved inside the per-line loop.  (HIGH)

2. arp -a parsing — the MAC regex required exactly 17 characters, but
     macOS strips leading zeros (e.g. "at 0:1e:c2:9:a:b"), so every
     device with a single-digit octet was skipped by the sweep.  Regex
     now accepts 1-2 digit octets; new helper _normalize_mac() zero-pads
     and lowercases so _known keys always match the tcpdump form.
     Fixed in the sweep regex, the ping-only ARP lookup, and the
     verification-ping MAC comparison.  (HIGH)

3. deviceStartComm — MACNumber (stored uppercase) was used un-lowered as
     a _known key, creating an orphaned duplicate entry and leaving the
     real entry without indigo_device_id until the first scan re-linked
     it (offline watchdog and passive-info updates were skipped in that
     window).  Now lowercased.  Same bug fixed in pingDeviceAction.  (HIGH)

4. pingDeviceAction — passed the device OBJECT instead of dev.id to
     _update_indigo_device_states, so the on-demand ping never updated
     the device and polluted the state-change history.  (HIGH)

5. Fingscan migration, step IMPORT — importNamesFromFingscan logged the
     matches but never wrote the fingscanDeviceInfo state, so the
     subsequent OVERWRITE step found nothing to rename.  The state is
     now actually written.  (HIGH)

6. MAC2Vendor.py — os.mkdir path had a stray quote ("indigo'"), so on a
     first run without ~/indigo a misnamed directory was created and the
     mac2Vendor subdirectory creation then failed.  Also added the
     missing "import codecs" (NameError in the fallback open path).

7. addInternetAddressDevice — indigo.device.create was called without
     pluginId; now passes pluginId=PLUGIN_ID like all other create sites.

8. _ping_only_pending — iterated and wholesale-replaced without
     protection while two sweep threads (primary + secondary interface)
     can run concurrently; could raise "dictionary changed size during
     iteration" or drop pending ping-only candidates.  Now iterates over
     a snapshot and updates the dict in place.

9. ARP sweep — a device that answered plain ICMP had its remembered
     curlPort overwritten with None on every sweep, discarding the
     preferred-port hint used by the TCP fallback probe.  The port is
     now only stored when one was actually found.

10. External devices — pingInterval fallback default was 60 s while the
     Devices.xml default is 120 s; also guarded against an empty-string
     property value (int("") ValueError).

11. Fingscan dialog callbacks — compareFingscanToNetworkScannerDevices
     and overwriteDevNamesWithFingNames wrote valuesDict["MSG"] without
     a None guard (TypeError if invoked without a dialog).

Version 2026.5.43 (2026-04-22)

1. Home/Away aggregate — configurable OFF delay:
     New "Delay before OFF" option in the Network Devices — Home or Away device
     editor (0 / 10 / 20 / 30 / 60 / 90 / 120 / 180 seconds).
     When all participants go offline the device does NOT immediately flip to OFF;
     instead an internal countdown starts.  If any participant comes back online

     automations.

Version 2026.5.42 (2026-04-22)

1. Proxy-ARP false-positive fix for pingOnly mode:
     Many WiFi routers (e.g. UniFi) answer ICMP on behalf of recently-
     disconnected clients.  The ARP sweep resets last_seen via these proxy-ARP
     replies, so the offline threshold based on last_seen never expired —
     the device stayed online even with WiFi off.
     Fixed by tracking a new per-device timestamp ping_only_last_ping_ok that
     is updated only when the dedicated ICMP probe itself succeeds — never by
     the ARP sweep.  The offline threshold for pingOnly devices is now measured
     against ping_only_last_ping_ok instead of last_seen.
     At startup, online pingOnly devices have ping_only_last_ping_ok set to now
     (fresh baseline) so a stale JSON timestamp does not cause an immediate
     offline decision.  _load_state also resets the field to 0 on every
     restart so old-format JSON files are handled cleanly.

2. Proxy-ARP false-positive fix for confirm mode:
     a) Secondary TCP probe skipped after was_offline confirmation:
        After the offline-reconfirmation TCP check failed (correct), the code
        fell through to a secondary TCP probe that incremented curlUseless on
        every offline cycle.  Once curlUseless hit _CURL_USELESS_LIMIT the
        confirmation fallback switched to a second ICMP ping — which proxy-ARP
        answered, sending the device back online.
        Fixed by returning False immediately after was_offline confirmation,
        preventing the secondary TCP probe from running (and inflating
        curlUseless) when the device is genuinely offline.
     b) curlUseless limit + known port → stay offline:
        When curlUseless reaches the limit but curlPort is set (TCP has worked
        before), the confirmation no longer falls back to a second ICMP ping.
        TCP failure is taken as confirmation of offline instead.  Second ICMP
        fallback is kept only for devices where TCP has genuinely never worked
        (curlPort = None, i.e. pure IoT / no open ports).
     c) curlUseless reset to 0 when device goes offline:
        Ensures that the next offline→online cycle always starts with a TCP
        confirmation attempt rather than immediately hitting the useless limit.

3. Device config cache fix (pingMode not updating without plugin reload):
     closedDeviceConfigUi was calling _cache_put(dev) where dev.pluginProps
     still held the pre-save values — Indigo writes the new props only after
     closedDeviceConfigUi returns.  Changing pingMode in the device editor
     therefore had no effect until the plugin was reloaded.
     Fixed: cache is now updated directly from valuesDict (the dialog values
     that will become the new props) in both the hot-path (device already
     cached) and the cold-path (device not yet cached).

4. Home/Away aggregate Address column — compact IP format:
     When Flip Address / Notes is ON, the Address column for networkDevicesHomeAway
     devices now shows a compressed form when all participants share the same /24
     subnet: "192.168.1. 112 22 44" instead of full padded IPs.
     Falls back to space-separated full IPs when participants span different subnets.
     The Notes column already used this format; the Address column now matches.

Version 2026.5.41 (2026-04-22)

1. Per-device Online Ping Interval (new device setting):
     New "Online Ping Interval" menu in the Network Device edit dialog.
     Options: 0 (default: 60 s in Ping only mode, scan interval in other
     modes), 30 s, 60 s, 90 s, 120 s, 180 s, 300 s, 600 s.
     Controls how often a device that is already online is actively pinged,
     independently of the global scan interval.  For Ping only mode this
     replaces the fixed 60 s constant; for other active ping modes (confirm,
     both, online, offline) a separate online_check_next_probe timer gates
     mid-cycle calls.  Label suggests setting this to 30–50 % of the Offline
     Threshold so the device is confirmed at least twice before it can time out.

2. pingOnly probe schedule now independent of scan interval:
     _scan_loop previously called _check_all_devices once per scan interval
     (e.g. every 2 min).  pingOnly devices' 60 s / 15 s adaptive timer could
     never fire more often than the scan interval, so a 90 s offline threshold
     would time out before the next ping confirmation.  Fixed: _scan_loop now
     calls _check_all_devices every _PING_ONLY_INTERVAL_OFFLINE (15 s) between
     ARP sweeps.  Per-device ping_only_next_probe gates prevent redundant work
     for devices not yet due; the sweep-freshness skip prevents re-probing
     ARP-visible devices too.

3. Sweep-freshness skip revised for pingOnly devices:
     pingOnly devices are now excluded from the ARP-based sweep-freshness check
     (their last_seen is set by ping, not ARP, so the ARP window was blocking
     the ping_only_next_probe timer).  A narrow coincidence guard replaces it:
     if the ARP sweep pinged the same IP within the last _SWEEP_FRESHNESS_MARGIN
     (10 s), the dedicated pingOnly probe is skipped for that cycle and the
     next_probe timer is pushed forward — preventing the double-ping that
     previously appeared in the log.

4. Bug fixes:
     - Lock ordering: _check_one now reads the device IP from _dev_cache under
       _dev_cache_lock rather than calling _cache_states() (which acquired
       _dev_cache_lock internally) and then immediately acquiring _known_lock —
       a potential lock-order inversion that could cause intermittent deadlocks.
     - Manually-created devices (e.g. MAC 00:00:11:00:00:01) with pingMode =
       pingOnly never pinged because no ARP/sniff history meant ip="" and
       _check_one returned early.  IP is now fetched from the device cache
       (ipNumber state) when _known has no entry for the MAC.
     - Results loop used ip from the pre-probe snapshot; _check_one may have
       populated _known[mac]["ip"] from the device cache during the probe, so
       the live _known value is now read inside the lock for the results loop.
     - Device ID race: a concurrent ARP/sniff thread can update
       _known[mac]["indigo_device_id"] between probe completion and the results
       loop, causing _update_indigo_device to update the wrong device.  Fixed
       by passing snapshot[mac]["indigo_device_id"] directly to
       _update_indigo_device (new dev_id parameter) so it updates the exact
       device that was probed.

Version 2026.5.33 (2026-04-21)
1. Synthetic (ping-only) device creation is now opt-in, default OFF:
     A new PluginConfig option "Create Synthetic Devices for Ping-Only Hosts"
     (syntheticDevicesEnabled, default false) gates all creation of
     00:00:00:00:00:XX synthetic MAC devices.  Previously, any IP that
     responded to ping but had no ARP entry (e.g. because a proxy-ARP router
     answers on behalf of the whole subnet) would eventually produce a fake
     Indigo device — flooding the plugin with hundreds of Net_00:00… entries.
     Existing tracking in _ping_only_pending is unaffected; enable the option
     only if you genuinely have devices on a separate VLAN that never appear
     in ARP.

     The gate is enforced in two places:
     a) _arp_sweep: the creation branch hits `continue` before _register_device
        is ever called with a synthetic MAC.
     b) _ensure_indigo_device: a hard `return` fires for any 00:00:00:00:00:XX
        MAC when the feature is off, regardless of how _ensure_indigo_device
        was reached (new device, existing-synth refresh, startup reload, etc.).
        This is the single authoritative block — no code path can bypass it.

2. _ping_only_pending now tracks (first_seen_ts, sweep_count) tuples:
     Synthetic device creation now requires BOTH _PING_ONLY_NEW_DEVICE_DELAY
     seconds (300 s) AND _PING_ONLY_MIN_SWEEPS consecutive sweeps (5) of
     seeing the IP without any ARP reply.  Previously only the time threshold
     was checked; many IPs could accumulate in _ping_only_pending and all
     expire in the same sweep, creating a burst of fake devices.

     Additionally, before any synthetic device is created, the plugin now
     sends an independent verification ping (ping -c 2) directly to the IP.
     The ARP sweep uses a fast broadcast flood that a proxy-ARP router can
     intercept; this single-host ping mirrors what a user would run from a
     terminal.  If the verification ping fails the IP is discarded as a
     false positive and never retried.

5. New Indigo device creation suppressed during startup grace period:
     _ensure_indigo_device no longer calls _create_indigo_device while
     in_grace_period is True.  Previously the grace period only gated
     offline decisions; brand-new MACs seen during startup (from proxy-ARP
     ghosts, one-shot probe frames, or the router answering on behalf of
     clients) would immediately get permanent Indigo devices.  Existing
     devices (loaded from known_devices.json) are still updated normally;
     only genuinely-new MACs are deferred until after the grace period ends.

3. Draytek / proxy-ARP TCP suspension (curlPingMismatch):
     When ping consistently fails but the TCP curl probe succeeds, the plugin
     now counts consecutive mismatches.  After _CURL_USELESS_LIMIT (5) in a
     row it auto-suspends TCP probing for that device (sets curlUseless to the
     limit) and logs a warning.  Resets when ping succeeds again.  Prevents a
     router that answers any TCP connection from keeping devices permanently
     marked online.

4. Fixed NameNotUniqueError crash in _create_indigo_device:
     If Indigo rejects device.create() with NameNotUniqueError (race between
     two threads or a disabled device with the same name), the code now
     searches all devices (including disabled) via indigo.devices.iter() to
     find the existing device and reuse it instead of crashing.

1. Ping replaced with pure Python SOCK_DGRAM/IPPROTO_ICMP socket — no subprocess,
   no /sbin/ping, no root required. One syscall per probe.
2. curl TCP probe replaced with pure Python SOCK_STREAM socket connect on ports
   80/443/22/8080. No subprocess. ConnectionRefusedError counts as alive.
   Winning port remembered per device in known_devices.json; tried first next time.
   After 5 consecutive all-port failures the probe is suspended per device
   (auto-resets when ping next succeeds).

   (routers, cameras, printers) so only ICMP ping decides online/offline.

   and TCP probe result to plugin.log (level debug, can be noisy).

   DHCP (67/68) instead of all traffic — ~95% CPU reduction.
   Per-MAC throttle raised from 5 s to 30 s.

Version 2025.0.7 (2026-04-16)
1. Passive sniffing upgraded: tcpdump now captures ALL ethernet traffic, not just ARP.
   Any packet from a device updates its last-seen timestamp.
   Catches devices that suppress ARP (iOS privacy mode, VMs, IoT, etc.).
   Each MAC throttled to one Indigo update per 5 s to avoid API flooding.

Version 2025.0.5  (2026-04-15)
-------------------------------
INSTALLATION
  No third-party packages required.
  All discovery uses macOS built-in tools:
    • /usr/sbin/tcpdump  — passive ARP sniffing
    • /sbin/ping         — subnet sweep and reachability checks
    • /usr/sbin/arp      — reads ARP cache after ping sweep

  Optional vendor name lookup:
    pip3 install manuf

CONFIGURATION  (Plugins → Network Scanner → Configure…)
  Network Interface       : interface to scan, default en0 (WiFi)
  Scan Interval (seconds) : how often to ping known devices, default 60s
  Offline Threshold (sec) : how long a device must be unreachable before
                            marked offline, default 180s (3 min)
  Enable ARP Sweep        : active subnet sweep on each scan interval
  Enable Passive Sniffing : listen for ARP traffic between sweeps
  Auto-Create Devices     : automatically create an Indigo device for
                            each new MAC address discovered
  Device Folder Name      : Indigo folder for Net_* devices, default
                            "Network Devices" (created automatically)

PLUGIN MENU  (Plugins → Network Scanner)
  List All Discovered Devices : prints all known MACs to the Indigo log
                                with IP, online status, vendor, last seen
  Force Immediate Rescan      : triggers an ARP sweep + ping check now
  Manage Ignored MAC Addresses: opens a dialog to exclude specific devices
                                from being created or updated

DEVICE DETAILS
  Each discovered device is named  Net_AA:BB:CC:DD:EE:FF
  Address column : MAC address (with colons)
  Notes column   : IP address with last octet zero-padded (192.168.1.005)
                   — enables correct alphabetical sort by IP
  States:
    onOffState   : True = reachable, False = offline
    ipAddress    : last seen IP address
    macAddress   : MAC address
    vendorName   : manufacturer (requires manuf package)
    lastSeen     : timestamp of last successful ping  YYYY-MM-DD HH:MM:SS
    created      : timestamp when Indigo device was first created

IGNORED MACs
  Via Plugins menu → Manage Ignored MAC Addresses:
    • Top list shows all discovered devices — click one, then click
      "▼ Ignore Selected Device" to exclude it
    • Bottom list shows currently ignored devices — click one, then click
      "▲ Un-ignore Selected Device" to re-enable it
    • Click OK to save
  Ignored devices are neither created nor updated by the scanner.

OFFLINE LOGIC
  A device is marked offline only after it has failed to respond to pings
  for longer than the configured Offline Threshold (default 3 minutes).
  A single missed ping does not immediately flip the device offline —
  this avoids false alarms from brief network blips.
